# CampusFlow Living Specification

AUCSC 325 final project · Final project draft revision 0.3 · Finalized 25 November 2026

Source baseline: a02b7ed392ba68c5868b7ba6929cb2be0dcc76e2 on origin/main.

## Purpose and scope

CampusFlow brings academic work, personal tasks, routines, classes and campus events into one daily student workflow. Today answers what needs attention now and what is coming next. CampusFlow remains useful without Canvas and does not submit coursework or replace university systems.

This draft describes the audited implementation and its limits. Implemented means the workflow exists in source; it does not certify current native behavior or production readiness.

## Implemented functionality

- Today derives an authenticated daily plan from separate saved entities, with upcoming work, Main Goal selection, progress, quick capture, next-class information and study windows.
- Personal tasks support creation, editing, deletion, completion/undo, separate schedules and deadlines, recurrence, priorities, categories, search, snooze, estimates, checklist steps and reusable templates.
- Academics supports student-created courses, manual coursework and exams, grade groups and targets, local what-if calculations, study tasks and retry-safe preparation plans.
- Canvas personal-token mode imports supported courses, assignments and their submission states, scores/groups, planner to-dos and private course calendar events. Imports update existing identities, preserve data after failed reads and reconcile removals only with complete source coverage.
- Campus discovery uses normalized provider records and reviewed Augustana calendar feeds. Students browse, search, inspect, save, include events in Today and configure reminders.
- Routines support daily/weekday schedules and weekly targets, goal-local completion/skip history, pause/resume, snooze, streaks and a starter library.
- Focus supports timed blocks, breaks, explicitly saved study history, checkpoint recovery and weekly reports. Daily and weekly reviews use recorded activity and reviewed scheduling actions.
- Non-medical wellness includes optional mood, energy, stress and notes, version-checked journal editing, reflection and breathing. Gym adds programs, workout logging, progression, own exercises/programs, imports, body-weight history and saved opening hours. Nutrition adds goals, food/meal logging and dining menus with estimated macros.
- Account features include authentication, session validation, data export, confirmed deletion and local cleanup. Help and guided setup use existing workflows.
- The current interface defines Today, Tasks, Campus, Wellness, Gym and Settings tabs, with a desktop web sidebar. PR #220 removes keyboard hiding, while PR #221 corrects native tab-bar height and safe-area padding overrides; current hardware acceptance remains pending.

## Partial and incomplete functionality

Notifications reconcile server intent with local Expo schedules and honor categories, permissions and quiet hours. Task/goal/event reminders use explicit instants; academic reminders use configured deadline lead times. Recurring task alarms do not automatically renew, and recurring goal alarm generation is deferred. Date-only task/goal reminder inputs can be accepted without delivery, and half-configured API quiet hours can silently disable suppression.

The morning overview is a generic 08:00 account-zone notification scheduled for seven days ahead, opening Today. It does not contain the example's live daily counts or nearest-deadline summary. An evening notification is not implemented.

Institutional Canvas OAuth remains unapproved and unimplemented. Automated Canvas suites use controlled responses; repository reports of limited personal-token operation do not establish comprehensive live-tenant acceptance. Email verification and recovery code exists, but real mail delivery is disabled by the course-prototype decision; signup does not prove mailbox ownership.

The Android widget, Lighthouse target and complete new-user production acceptance remain outstanding. A broader Student Life directory, custom categories, automatic priority/scheduling, pets/currency/shops, social features and health-platform integrations remain outside the required MVP.

## Architecture and data rules

The npm TypeScript monorepo contains an Expo mobile app, one modular NestJS API and independent contracts/domain packages. Only the API accesses PostgreSQL and Canvas. Personal tasks, academic items, goals, events, wellness and training records retain their own identities; Today is derived.

PostgreSQL is authoritative. Account-scoped SQLite supports previously loaded reads and device drafts, with visible freshness and coverage. Missing data remains unknown. General offline writes and conflict synchronization are not supported. Focus recovery excludes uncertain closed-app time; workout drafts are local state, with online saving on Finish or after the defined inactivity period.

Timed values use UTC, date-only values remain calendar dates, and recurrence retains IANA zones. Local day bounds account for daylight saving. Canvas tokens are sealed by the backend and excluded from response DTOs. Existing-server PostgreSQL and PC/server CI supersede the original Supabase/GitHub Actions deployment assumptions under the later ADRs.

## Known defects and limitations

The native tab-bar collapse is addressed in merged PR #221. PR #220 removed keyboard hiding but did not fix the collapse; post-#221 hardware behavior remains unverified. Canvas has concluded-course, excused-work, missing-coverage and stale-status defects (#182, #183, #188, #189). Reminder/API gaps include recurring alarms, date-only inputs, ignored goal-snooze occurrence identity, whitespace titles, incomplete quiet hours and finished-work Main Goal selection (#184, #190, #191, #196–#198).

Capacity and privacy risks include broad planning reads, unbounded Canvas response bytes, sync persistence-failure/backoff behavior, account enumeration and password hashing under a database lock (#185, #192–#195). Session/task-retry retention remains a gap; expired recovery/verification tokens and rate buckets already have cleanup and automated tests.

The malformed reminder-suppression cache bug is fixed in merged PR #142. Schema-invalid decoded data now enters conservative, account-scoped recovery until a current server read authorizes reminder IDs. Invalid JSON, failed durable writes, older-client compatibility and failed native cancellation retain the documented limits.

Local schedules learn backend changes on successful refresh; offline devices cannot receive immediate deadline cancellation. Android delivery can be inexact. Notification schedules and the reminder center are not proof of delivery.
